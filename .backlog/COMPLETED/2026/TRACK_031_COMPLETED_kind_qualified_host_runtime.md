# TRACK 031 [COMPLETED]: Kind-qualified HostRuntime and trusted bundled activation adapter

Problems (PORE)
- P1: As a host maintainer, I cannot retain or validate the stable origin and trusted policy metadata of each capability, because the current registry identifies Tools only by their flat endpoint-visible names.
- P2: As a maintainer testing or assembling MyMCP, I cannot supply one explicit immutable runtime to MCP handling and application assembly, because method dispatch imports a globally composed startup registry and ordinary package imports transitively compose production state.
- P3: As a future plugin author and security reviewer, I risk the current anonymous synchronous Mnemosyne integration being frozen as an unknown-author execution ABI, because no trusted bundled activation adapter distinguishes reviewed in-process composition from the later isolated external boundary.
- P4: As a user relying on Mnemosyne, I risk runtime-foundation work changing existing public behavior, startup gates, configuration timing, or storage behavior unless the new contracts and injection seams preserve those compatibility boundaries under automated and direct protocol validation.

Objective
- Establish the kind-qualified immutable host runtime, trusted Mnemosyne bundled activation adapter, explicit bootstrap, and runtime injection required by Phase 1 without changing the public Mnemosyne compatibility surface.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- Execute one declared coherent TDD chunk at a time and update this Track immediately after validation.
- Preserve local-first operation, single-user scope, filesystem truth, least privilege, explicit Tools, operator enablement, and per-call mutation consent.
- Preserve `/mcp`, `/health`, `/version`, server identity and marker, `list_tools`, every current `memory_*` name/order/schema/result/error, client compatibility normalization, independent mutation gates, `MNEMOSYNE_*`, `~/.mnemosyne`, memory formats, paths, logging, and storage behavior.
- Keep HTTP transport thin, MCP semantics under `mymcp/mcp/`, generic plugin contracts under `mymcp/plugin/`, immutable runtime assembly under `mymcp/host/`, and Mnemosyne policy outside generic host packages.
- Only explicit host bootstrap may import the concrete trusted Mnemosyne adapter; generic runtime and plugin contracts must not import Mnemosyne configuration, memory, or Tool packages.
- Trusted effect and consent metadata remain internal host contract values and must not be derived from or automatically projected as public MCP annotations.
- The trusted synchronous Mnemosyne adapter must not be presented or frozen as the unknown-author external execution ABI.
- Candidate composition must fail without returning or publishing a partial runtime.
- Do not introduce shell execution, unrestricted filesystem/network access, secret storage, arbitrary imports, configured-module discovery, entry-point discovery, or dynamic loading.

Risks / decisions
- Risk: Adding future lifecycle or external-worker semantics to the first contracts could freeze an unproven or unsafe ABI.
- Mitigation: Implement only values and trusted bundled seams required by Phase 1; defer manifests, external adapters, and lifecycle behavior explicitly.
- Risk: Changing startup ownership could alter when Mnemosyne settings resolve or cause repeated reads.
- Mitigation: Preserve one startup-fixed settings resolution per runtime bootstrap and lazy root resolution only after Tool-specific validation.
- Risk: Runtime injection could change JSON-RPC, route, notification, or argument-normalization behavior.
- Mitigation: Drive each seam with focused tests and retain existing complete protocol and route suites as compatibility evidence.
- Risk: Import refactoring could create cycles or break `mymcp`, `mymcp-dev`, or `mymcp.app:app` startup.
- Mitigation: Establish runtime-bound dispatch and application factories before removing global composition, then validate imports and both CLI modes.
- Risk: Metadata-bearing composition could accidentally expose internal policy values publicly.
- Mitigation: Keep public discovery projections unchanged and test that trusted metadata remains internal.
- Risk: Existing tests depend on `mymcp.mcp.startup.REGISTRY` identity and module-level application assembly.
- Mitigation: Replace global-singleton assertions only when equivalent explicit-runtime behavior is covered; do not weaken observable compatibility tests.
- Decision: Follow `docs/PLUGIN_ARCHITECTURE.md` Phase 1 and the reconciled living roadmap revision 4 as the authoritative target and delivered baseline.
- Decision: Host API v1 is Tools-only and qualified capability identity is `(plugin_id, capability_kind, capability_local_id)`.
- Decision: Public Tool names are host-owned bindings; current Mnemosyne `memory_*` names remain canonical compatibility bindings and `list_tools` remains host-reserved.
- Decision: The runtime generation is opaque and independent of endpoint, package, plugin, capability-contract, protocol, and record-schema versions.
- Decision: Phase 1 wraps one canonical existing Mnemosyne implementation; it neither copies nor relocates domain code.

Decision log
- Decision: TRACK_030's corrected first implementation boundary is adopted unchanged: frozen logical metadata, immutable `HostRuntime`, trusted Mnemosyne adapter, explicit bootstrap, and runtime injection, with exact public compatibility and all later phases deferred.
- Decision: The working tree already contains unrelated uncommitted changes to `AGENTS.md` and `opencode.json`; this Track must not modify, overwrite, stage, or attribute those changes to its work.
- Decision (Q1): `mymcp/plugin/contracts.py` will own frozen validated plugin ID, semantic plugin version, Tools-only capability kind, capability-local ID, qualified capability ID, trusted Tool effects, consent requirement, and public binding values. `mymcp/plugin/composition.py` will own `ActivatedTool` and ordered `PluginContribution` values containing only the selected Tool definition/invoker and metadata needed for complete composition. These values contain no manifest, complete `PluginDefinition`, activation context, health, shutdown, lifecycle, artifact, worker, or external execution contract. The contribution boundary defensively snapshots Tool definitions so later caller mutation cannot alter validation, binding, discovery, or runtime state.
- Decision (Q1): Plugin IDs use bounded lowercase kebab identity and capability-local Tool IDs use bounded lowercase underscore identity, each at most 64 characters and rejecting `__`. Host API v1 admits only capability kind `tool`. Plugin versions use strict bounded SemVer text and do not imply host, endpoint, protocol, capability-contract, generation, or record-schema versions. Trusted effect dimensions require actual booleans; consent is exactly `none` or `per_call`.
- Decision (Q2): Keep `mymcp.mcp.tool_registry.ToolRegistration` unchanged as the generic MCP definition/handler pair. Metadata-bearing `ActivatedTool` values sit above it and are projected through complete host-owned bindings into defensively copied registrations only during generic plugin composition. Binding validation requires exactly one binding for every selected qualified capability, no unknown or unselected binding, no duplicate qualified identity, and no duplicate public name. `list_tools` and names beginning `mymcp_` are host-reserved; Phase 1 does not invent a narrower public-name grammar than the current nonempty MCP Tool-name contract.
- Decision (Q2): Host-owned `list_tools` is not a plugin capability and receives no fabricated plugin identity or plugin effect/consent metadata. Runtime origin uses a distinct host-origin value for `list_tools` and qualified plugin origins for contributed Tools. The host Tool remains first and is bound to the final post-binding public Tool definitions.
- Decision (Q3): MCP protocol helpers will return transport-neutral JSON-compatible dictionaries, and an immutable runtime-bound dispatcher in `mymcp/mcp/` will accept a small structural runtime contract exposing the final `ToolRegistry`. It will not import bootstrap, concrete plugins, Mnemosyne configuration, or a module-global registry. HTTP conversion to `JSONResponse`, notification `202` handling, and request/response logging remain exclusively in `mymcp/routes/mcp.py`.
- Decision (Q3): `create_app(runtime)` will require an explicit runtime and will install an MCP router bound to that runtime's dispatcher. This permits two independently composed runtimes and applications in one test process without global monkeypatching or cross-runtime discovery/dispatch.
- Decision (Q4): Add `create_production_app()` as the explicit production assembly boundary; it imports/calls host bootstrap inside the factory and then delegates to `create_app(runtime)`. Console commands will point Uvicorn to `mymcp.app:create_production_app` with factory mode, including reload mode. Remove the module-level application export from `mymcp/__init__.py`; importing `mymcp`, `mymcp.app`, or generic plugin/MCP/host modules will not resolve Mnemosyne settings or compose a runtime.
- Decision (Q4): After all references migrate and compatibility tests pass, remove obsolete `mymcp/mcp/startup.py` and transitional `mymcp/mcp/composition.py`. The HTTP routes and console commands remain stable, while the replacement ASGI factory target is documented because direct use of the undocumented internal `mymcp.app:app` object will no longer work.
- Decision (Q5): `mymcp/host/runtime.py` will own validated opaque `RuntimeGenerationId` and immutable `HostRuntime`. Runtime construction accepts a zero-argument generation factory for deterministic tests and defaults to a UUID-derived opaque value in production. The factory runs only after plugin, capability, binding, reservation, collision, registration, and host-Tool validation succeeds; its result is validated before the complete runtime is returned, so failed composition exposes no partial runtime or registry.
- Decision: `HostRuntime` retains the final registry, ordered plugin inventory, public-name origins including the distinct host origin, qualified effect/consent metadata, qualified-to-public bindings, and generation identity through immutable or defensive collections. It remains domain-neutral and imports no concrete plugin or Mnemosyne policy.
- Decision: The trusted Mnemosyne adapter emits the same generic `PluginContribution` consumed by composition, wraps the canonical current `build_mnemosyne_registrations()` behavior, and preserves settings-once selection plus lazy per-valid-operation domain construction. Its independent initial internal plugin version is `0.1.0`, not derived from host/server `0.1.4`; Phase 2's manifest will retain it unless a separately approved plugin-version decision changes it.
- Decision: `mymcp/host/bootstrap.py` is the sole generic-host module allowed to import the concrete trusted Mnemosyne adapter. It declares adapter order and pinned compatibility bindings explicitly, performs no dynamic discovery, and constructs one complete production runtime.
- Decision: Trusted Phase 1 metadata classifies recall/list/inspect as read-only, remember/archive/restore as non-destructive mutations, and revise/forget as destructive because prior content is not retained; every Tool is local (`open_world=false`) and idempotent in the no-additional-effect sense, including forget even though a repeated request returns `not_found`; every mutation requires `per_call` consent while reads require none. These values remain internal and are not projected as MCP annotations.
