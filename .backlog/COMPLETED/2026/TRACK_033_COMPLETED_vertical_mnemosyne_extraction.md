Problems (PORE)
- P1: As a MyMCP host maintainer, I cannot treat Mnemosyne as one coherent bundled plugin, because its canonical production implementation is split across host-generic, integration, configuration, Tool, and memory-domain locations.
- P2: As a future plugin author, I cannot rely on the documented bundled-plugin ownership boundary, because the only current plugin package contains an inert declaration while its adapter, configuration, domain, and MCP implementation remain elsewhere.
- P3: As a Mnemosyne user, I risk compatibility or state-coordination regressions during structural extraction, because the move crosses public Tool adapters, startup settings, lazy storage composition, process-shared cursor state, mutation locks, and filesystem persistence.
- P4: As a host architect, I cannot enforce domain-neutral generic MCP and host layers, because concrete Mnemosyne Tool and integration modules still live under `mymcp/mcp/` and its domain remains under top-level transitional packages.

Objective
- Move the single canonical Mnemosyne configuration, memory domain, MCP adapters, Tool definitions and handlers, and trusted plugin adapter into `mymcp/plugins/mnemosyne/`, remove transitional implementation locations, and preserve the complete Mnemosyne 0.1.4 public and storage contract.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- Execute one declared coherent TDD chunk at a time and update this Track immediately after validation.
- Preserve local-first operation, single-user scope, filesystem truth, least privilege, explicit Tools, operator enablement, and per-call mutation consent.
- Preserve `/mcp`, `/health`, `/version`, the Mnemosyne 0.1.4 server marker, plugin `mnemosyne` version `0.1.0`, `list_tools`, every current `memory_*` name/order/schema/result/error, `MNEMOSYNE_*`, `~/.mnemosyne`, storage, records, logging, and consent behavior.
- Preserve startup-fixed independent mutation gates, settings resolution exactly once, lazy memory-root resolution after Tool validation, lazy first-run initialization, process-shared list-cursor state, and the per-root mutation-lock registry.
- Move one canonical implementation atomically. Do not duplicate or re-export domain classes, cursor codecs, lock registries, policy, handlers, storage implementation, configuration, or Tool adapters under old and new module identities.
- Keep `list_tools`, argument normalization, registry, dispatch, JSON-RPC semantics, runtime assembly, routes, application assembly, and public bindings host-owned and domain-neutral.
- Only explicit host bootstrap may import the concrete bundled Mnemosyne plugin. The plugin may depend on generic plugin/MCP contracts and its own packages, but not routes, application assembly, host bootstrap, another plugin, dynamic discovery, or unrestricted host state.
- Preserve fixed packaged-manifest loading and exact manifest/definition/selected-contribution parity before runtime generation. Extraction grants no authority and adds no discovery, configured import, entry point, installation, network access, or external execution.
- Do not perform the MyMCP public-host identity cutover in this Track.

Risks / decisions
- Risk: Moving domain modules in separate implementations could split process-shared cursor validity or mutation-lock coordination.
- Mitigation: Move the complete memory package in the same atomic vertical chunk as every consumer and prohibit duplicate domain modules or shims.
- Risk: Moving Tool packages incrementally could leave generic MCP importing concrete plugin code or plugin code depending on transitional host-domain paths.
- Mitigation: Move the coupled configuration, domain, Tool, adapter, and bootstrap-import boundary in one atomic TDD chunk driven by final ownership tests.
- Risk: Import-only changes mask accidental public Tool schema, ordering, handler, or error drift.
- Mitigation: Compare canonical definitions and production behavior exactly, retain all 16 gate combinations, and run complete compatibility plus direct MCP checks.
- Risk: Configuration relocation changes `Path.home()` timing, environment precedence, file-read count, failure order, or lazy root behavior.
- Mitigation: Keep the configuration implementation semantically unchanged and drive relocation with timing, source-safety, and startup tests.
- Risk: Packaging tests freeze an obsolete two-file inventory or omit the extracted Python implementation from the wheel.
- Mitigation: Test required canonical plugin contents and forbidden transitional contents while keeping `manifest.json` as the only explicit package-data resource; do not treat Python modules as package data.
- Risk: Structural extraction is conflated with public MyMCP identity migration or external-plugin activation.
- Mitigation: Keep Mnemosyne 0.1.4 host compatibility fixed and document cutover, installation, isolation, lifecycle, and gateway work as separate later Tracks.
