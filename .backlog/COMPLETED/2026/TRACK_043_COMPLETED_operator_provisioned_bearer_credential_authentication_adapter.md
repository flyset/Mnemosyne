Problems (PORE)
- P1: As a MyMCP operator, I cannot enroll a local client as a registered principal, because production Authentication has no supported bearer-credential adapter or approved non-secret credential-verifier source.
- P2: As the MyMCP maintainer, I cannot add bearer authentication safely, because credential parsing, verifier handling, rotation, revocation, and failure behavior are not yet bounded without weakening exact routing or exposing evidence.
- P3: As a Mnemosyne user, I need bearer authentication to preserve configured anonymous access and existing MCP behavior, because Authentication must remain upstream of MCP, Governance, the plugin runtime, plugins, and plugin data.

Objective
- Deliver one startup-fixed operator-provisioned bearer-credential adapter that validates exactly routed Authorization bearer evidence into the existing normalized registered-principal contract without exposing credentials or adding authorization policy.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- Follow the documented layer order: HTTP server, Authentication, MCP server, Governance, Plugin runtime, Plugin, and Plugin data or external service.
- Host configuration is not credential, token, verifier, or secret storage. Any configuration evolution may contain only approved bounded non-secret source metadata.
- Credentials and raw evidence never reach representations, logs, errors, normalized principals, MCP, Governance, plugins, plugin data, durable project memory, or downstream handlers.
- Submitted evidence routes by one exact host-derived descriptor to one enabled adapter. There is no probing, adapter-order behavior, downgrade, cross-adapter fallback, or fallback to anonymous.
- Both GET and POST `/mcp` authenticate before streaming, body parsing, MCP logging, or dispatch; failure retains the empty HTTP 401 contract.
- Adapter configuration and verifier state are immutable for one process start. Changes require explicit operator action and restart.
- Authentication remains transport-neutral and standard-library-only. HTTP routes own only bounded evidence extraction and transport outcomes.
- The host retains canonical principal construction. The adapter returns only one validated stable adapter-local subject or one bounded failure.
- Bearer authentication establishes principal identity only; it grants no Tool authority, Governance allowance, user consent, approval, plugin trust, or process isolation.
- Preserve current schema-1/schema-2/absent-file anonymous compatibility and explicit schema-3 anonymous behavior unless an approved version-impact decision says otherwise.
- Do not add OAuth, sessions, Governance policy, filtered discovery or dispatch, exact-call approval, security audit, remote or multi-user trust, plugin changes, credential-management HTTP/MCP endpoints, or secret-management infrastructure.

Risks / decisions
- Risk: Operator-provisioned bearer and future OAuth commonly use the same Authorization bearer route. Without a trustworthy host-derived profile, they cannot coexist on the same exact descriptor and must not be distinguished by token shape, sequential validation, or adapter order.
- Risk: Plaintext credential storage, a weak verifier algorithm, unsafe file permissions, source replacement races, or insufficient entropy could defeat the security boundary.
- Risk: Subject lookup, verifier comparison, and distinguishable failure behavior could disclose credential or enrollment information through timing, errors, or logs.
- Risk: Rotation and revocation can become ambiguous if immutable startup state and restart requirements are not reflected in one complete replacement workflow.
- Risk: Evidence grammar differences across clients can create accidental incompatibility unless casing, whitespace, character, encoding, duplicate-header, and size rules are explicit.
- Risk: Adding method-specific source settings directly to schema 3 could change a published strict schema without an explicit schema-version decision.
- Decision: This Track consumes the contract-version-1 router and normalized principal foundation from TRACK_042; it does not move bearer semantics into MCP, Governance, plugins, or plugin data.
- Decision: The bearer adapter is host-owned Authentication infrastructure, not a Tool plugin and not part of the external plugin-author contract.
- Decision: Activation will authorize only the declared TDD chunks one at a time. It will not authorize roadmap mutation, commit, push, tag, or release publication.
- Decision: The approved credential is exactly `mymcp1.<credential-id>.<secret>`, where `credential-id` is 32 lowercase hexadecimal characters and `secret` is the 43-character unpadded RFC 4648 base64url encoding of 32 independently random bytes. It is accepted only in one `Authorization` field as case-insensitive ASCII scheme `Bearer`, one ASCII space, and that exact ASCII credential with no leading/trailing whitespace, tab, Unicode, empty/extra component, padding, or alternate alphabet.
- Decision: The verifier snapshot is strict UTF-8 JSON, at most 16 KiB, with duplicate JSON keys rejected and exact top-level shape `{"format_version":1,"credentials":[...]}`. It contains 0-32 exact records with fields `id`, `subject`, and `digest`; `id` uses the credential-ID grammar, `subject` uses the unchanged Authentication-v1 subject contract, and `digest` is the 43-character unpadded base64url SHA-256 digest of the secret. Unknown fields, missing fields, invalid encodings or lengths, duplicate IDs, and more than 32 records fail startup. Multiple IDs may intentionally map to one subject for rotation.
- Decision: Verification parses the fixed credential grammar, selects by credential ID, computes SHA-256 over the decoded 32-byte secret, and uses `hmac.compare_digest` on fixed 32-byte values. Unknown IDs perform the same digest computation and compare against one fixed in-memory dummy digest before returning the same bounded rejection. The adapter retains only immutable IDs, subjects, and digests, never plaintext credentials.
- Decision: A verifier source is one operator-selected absolute unexpanded local file. The path contains no NUL, `~`, environment syntax, or `.`/`..` component. Its immediate parent is a non-symlink/reparse directory and the source is a non-symlink/reparse regular file; on POSIX neither may be group/world writable and the file must have no group/world permission bits. Descriptor-relative/no-follow access is used where supported, with pre/open/post identity, type, size, permission, and source-state checks. Unsafe, unreadable, excessive, changing, invalid-UTF-8, or invalid-format sources fail closed without path, content, subject, credential ID, digest, exception, or traceback disclosure.
- Decision: Provisioning is an external offline operator responsibility, not a MyMCP command or API. The operator stops MyMCP, independently generates the credential and verifier record, delivers the credential once through a chosen secure channel, atomically replaces the complete protected snapshot, and restarts. Rotation adds a new ID for the same subject and restarts before the old ID is removed by another complete replacement and restart. Revocation removes the ID and restarts. There is no revoked marker, merge, runtime reread, environment credential, fallback, or hot invalidation.
- Decision: Host configuration schema 4 preserves schema-3 server, plugin, anonymous, and adapter declarations and adds the exact optional non-secret `[authentication.operator_bearer]` table containing only `verifier_path`. The table is required exactly when an `operator-bearer-v1` declaration exists, including a disabled declaration; its path is validated in all cases but the source is accessed only for an enabled adapter. Schemas 1-3 and absent-file defaults remain accepted and unchanged.
- Decision: The stable production adapter type is `operator-bearer-v1`. An enabled instance must claim exactly `EvidenceRoute("authorization", "bearer", None)`; exact-route collision rules mean at most one such instance can be enabled. No profile is inferred from credential shape, and disabled declarations remain inert.
- Decision: Request authentication emits no credential-, route-, adapter-, subject-, or enrollment-bearing log. Startup composition may report only a bounded outcome, enabled adapter count, and stable content-free error code. Every malformed, excessive, duplicate-header, unsupported, unknown, invalid, or rejected submitted credential maps to the existing empty HTTP 401 and invokes no MCP handling.
- Decision: Concrete Authentication methods are organized under `mymcp/authentication/adapters/`. Operator-bearer credential grammar, immutable verifier records, SHA-256 verification, strict JSON parsing, and protected source reading belong to `mymcp/authentication/adapters/operator_bearer.py` and remain standard-library-only and transport-neutral. Schema-4 parsing belongs to `mymcp/host/configuration.py`; source selection and production registration belong to `mymcp/host/authentication.py`; raw Authorization extraction and empty-401 transport mapping remain in `mymcp/routes/mcp.py`. Authentication imports no FastAPI, route, MCP, Governance, plugin, concrete plugin, or host-configuration module.
- Version impact: Delivering the first production registered-principal adapter and host configuration schema 4 advances the MyMCP distribution/package and endpoint/server marker from `0.5.0` to `0.6.0`. Host configuration adds schema 4 while schemas 1-3 and absent-file behavior remain unchanged. Authentication contract remains version 1 because principal, evidence, context, adapter result, exact routing, anonymous admission, and canonical principal construction are unchanged. The stable adapter type is `operator-bearer-v1`; its separately versioned verifier-source format is 1. MCP protocol/version negotiation, endpoint identity and routes, HTTP empty-401 failure shape, host plugin API 1, manifest schema 1, external plugin-author contract 1, worker protocol absence, every plugin identity/version, capability identity/version and public binding, plugin configuration/data schema, Governance policy revision absence, runtime-generation semantics, Mnemosyne configuration/data/record schemas, Tool discovery/dispatch, and all Mnemosyne behavior remain unchanged because the new behavior is confined to upstream Authentication and host startup configuration.
