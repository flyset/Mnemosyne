# TRACK 039 [COMPLETED]: MyMCP host configuration foundation

Problems (PORE)
- P1: As the MyMCP operator, I cannot declare host-level startup and composition intent in one stable host-owned configuration contract, because MyMCP currently has no overall host configuration boundary.
- P2: As the MyMCP operator, I need configuration to follow a recognizable user-configuration convention, because a mixed-purpose or surprising home-directory layout makes configuration harder to locate and manage consistently.
- P3: As the MyMCP maintainer, I cannot safely begin external plugin startup composition until configuration source selection, parsing, validation, ownership, failure behavior, and versioning are explicit and deterministic.
- P4: As the Mnemosyne user, I need the existing Mnemosyne configuration contract to remain independent, because host configuration must not migrate, duplicate, or reinterpret plugin-owned settings.
- P5: As the MyMCP operator, I cannot select an available loopback address and port through MyMCP's supported launchers, because both values are currently hard-coded.

Objective
- Define and implement a strict, versioned, immutable MyMCP host configuration snapshot that uses the standard XDG configuration location, configures supported launchers within the machine-local boundary, preserves bundled-only startup when absent, and establishes the desired-state input for later external plugin startup composition.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- The canonical configuration path is `$XDG_CONFIG_HOME/mymcp/config.toml` when `XDG_CONFIG_HOME` is set and valid; otherwise it is `~/.config/mymcp/config.toml`.
- Path resolution must follow the XDG Base Directory convention without probing, merging, or silently falling back to `~/.mymcp/config.toml`.
- Host configuration expresses process and startup-composition intent; it grants no consent, authority, trust proof, or safety assurance.
- Configuration is read at most once by each process that consumes it during explicit startup and represented within that process by one immutable snapshot; normal production reads exactly once overall.
- Supported launchers accept only literal loopback server addresses and integer ports from 1 through 65535; non-loopback operation remains outside the current threat model.
- Missing host configuration preserves the current bundled-only startup behavior.
- External plugins are never enabled implicitly.
- Disabled external plugins are not imported and expose no Tools.
- Configuration changes require server restart.
- MyMCP host configuration remains separate from plugin-owned configuration.
- Preserve every existing `MNEMOSYNE_*`, `~/.mnemosyne/config.toml`, and Mnemosyne storage, Tool, consent, and compatibility identity.
- Keep local-first, single-user, least-privilege, deterministic startup and fail-closed composition boundaries.
- Do not add host-managed plugin installation, dependency environments, hot activation, runtime lifecycle management, sandboxing, isolation, supervision, or plugin-safety claims.

Decision log
- Decision (Q1): Read `XDG_CONFIG_HOME` once during startup. An unset, empty, or relative value is ignored under the XDG convention and selects `~/.config/mymcp/config.toml`; an absolute value selects `$XDG_CONFIG_HOME/mymcp/config.toml`. Do not expand tildes, environment variables, or other substitutions inside the value, and do not canonicalize it with `resolve()` during selection. The selected directory need not exist, and an absent selected file means bundled-only configuration. An undecodable or otherwise unrepresentable value fails startup with a bounded error. Inaccessibility of the selected source is a configuration-source error and never triggers probing or fallback to another location.
- Decision (Q2): Apply the same deterministic contract on every platform. When no valid `XDG_CONFIG_HOME` is selected, use `Path.home() / ".config" / "mymcp" / "config.toml"`, including on native Windows; do not consult `%APPDATA%` or `%LOCALAPPDATA%`. On Windows, accept absolute drive and UNC paths but reject drive-relative paths such as `C:settings`. If the home directory cannot be determined when needed, fail startup with a bounded error.
- Decision (Q3): Add `mymcp/host/configuration.py` as the exclusive host owner of XDG path selection, safe bounded source reading, strict TOML parsing, immutable `HostConfiguration` and external-plugin declaration values, and stable configuration error codes/messages. It may use the standard library and generic host/plugin value types but must not import FastAPI, routes, MCP dispatch, or concrete plugins. `mymcp/host/bootstrap.py` calls the loader exactly once during production startup, receives one immutable snapshot, and uses it as composition input without owning path or TOML behavior; explicit tests and callers can instead inject a snapshot without reading user configuration. `mymcp/settings.py` remains limited to server/process identity constants; `mymcp/app.py`, routes, and `mymcp/mcp/` remain configuration-unaware; Mnemosyne configuration remains independent and is not reused. Configuration fails before runtime construction, and bootstrap propagates the configuration module's bounded errors without adding paths, values, or exception details.
- Decision (Q4, revised by Q9): Configuration schema version 1 uses required top-level integer `schema_version = 1`, one optional `[server]` table defined by Q9, and an optional ordered `[[plugins]]` array of tables. Each plugin table contains exactly required `id` and required native TOML boolean `enabled`; `id` conforms to the existing `PluginId` contract. A present file must declare `schema_version`, so an empty file is invalid; an absent file creates an immutable schema-v1 snapshot with server defaults and no external declarations. Reject unknown top-level fields/tables, unknown server/plugin fields, wrong types, and coercion. Do not add a general `[host]` table, manifest or implementation locator, entry point, public binding, plugin-owned configuration, or secret reference in this foundation. Phase 3 must explicitly version any schema expansion needed to locate external metadata or implementation code. The idiomatic repeated `[[plugins]]` form preserves declaration order and keeps plugin identity as validated data rather than dynamic table keys.
- Decision (Q5): Validate each declaration ID without trimming, case-folding, normalization, or repair by constructing the existing `PluginId` value: 1 through 64 lowercase ASCII characters, beginning with a letter and continuing as lowercase alphanumeric components separated by single hyphens. Reject duplicate declaration IDs regardless of enablement and reject IDs already owned by bundled plugins, including `mnemosyne`; bootstrap performs the bundled-inventory collision check without loading external code. Preserve exact file order in the immutable snapshot, and derive any enabled subset without sorting while preserving relative order. Require an explicit native TOML boolean `enabled` for every declaration; there is no default. Parsing performs no manifest access, package discovery, or implementation import. A declaration expresses desired state only and proves no installation, compatibility, authority, safety, or consent. Schema version 1 permits only `id` and `enabled`; loading-specific fields remain deferred to Phase 3. There is no separate plugin-count limit: the bounded configuration source supplies the resource bound, and Phase 3 may add a justified composition limit only if its actual validation or startup behavior requires one.
- Decision (Q6): Treat the selected XDG base as the operator-selected anchor. Validate the `mymcp` application directory and `config.toml` without rejecting a symlinked parent such as `~/.config`; an absent application directory or file means absent configuration. Reject a symlinked `mymcp` directory or `config.toml`, a non-directory application component, a non-regular source, and detectable Windows reparse points for either validated component. Bound the complete source to 64 KiB by reading at most 65,537 bytes, require strict UTF-8, parse with standard-library `tomllib`, and reject malformed TOML, duplicate keys, unknown fields, and wrong types. On POSIX, reject group- or world-writable application directories and files without requiring exact modes; document recommended modes `0700` and `0600`, and prohibit plaintext secrets. Where supported, open the application directory with no-follow/directory-only flags, open the file relative to that descriptor with no-follow, compare pre-open and post-open identity, verify descriptor types, and recheck permissions and size. Treat replacement or mutation during reading as a bounded source-change failure without retry or alternate-path fallback. On platforms lacking equivalent primitives, perform all available symlink/reparse, type, pre/post identity, size, and descriptor checks without claiming unavailable POSIX permission or no-follow guarantees, and fail boundedly when inconsistency is detected.
- Decision (Q7): `HostConfigurationError` carries exactly one stable code and its fixed message: `invalid_location` / `MyMCP configuration location is unavailable`; `unsafe_path` / `MyMCP configuration path is unsafe`; `not_regular` / `MyMCP configuration source is not a regular file`; `unsafe_permissions` / `MyMCP configuration source permissions are unsafe`; `unreadable` / `MyMCP configuration source could not be read`; `too_large` / `MyMCP configuration exceeds 65536 bytes`; `source_changed` / `MyMCP configuration changed while being read`; `invalid_utf8` / `MyMCP configuration is not valid UTF-8`; `invalid_toml` / `MyMCP configuration is not valid TOML`; `unsupported_schema_version` / `MyMCP configuration schema version is unsupported`; `invalid_schema` / `MyMCP configuration has an invalid schema`; `duplicate_plugin` / `MyMCP configuration contains a duplicate plugin declaration`; and `bundled_plugin_conflict` / `MyMCP configuration conflicts with a bundled plugin identity`. Missing configuration is normal and produces no error. Every error occurs before runtime or HTTP/MCP construction, returns no partial snapshot, triggers no alternate-location attempt, and includes no path, environment value, TOML content, plugin ID, field value, OS/parser detail, traceback detail, or underlying exception text. Suppress caught OS, Unicode, and TOML exception chaining. Q8 separately decides the code for a valid but currently unsupported enabled declaration.
- Decision (Q8): Parse and validate the complete present document regardless of declaration enablement; invalid configuration always fails startup, including when `plugins` is omitted or every declaration is disabled, and `enabled = false` never suppresses schema validation. An absent file or a valid file with no enabled plugins produces the unchanged bundled-only runtime. Before Phase 3, any valid `enabled = true` declaration, including one in a mixed enabled/disabled list, fails before runtime construction with code `enabled_plugin_unsupported` and fixed message `MyMCP external plugin enablement is not supported by this build`. Do not identify the plugin, access manifests, discover packages, import external code, return a partial snapshot, or silently ignore requested desired state. Phase 3 replaces this unsupported-state failure with validated startup composition.
- Decision (Q9): Schema version 1 includes an optional `[server]` table with independently optional `address` and `port`; defaults remain literal IPv4 loopback `127.0.0.1` and integer `8000`. `address` must be a native TOML string containing a literal IPv4 or IPv6 address for which the standard-library IP parser reports loopback, allowing values such as `127.0.0.1`, `127.0.0.2`, and `::1` while rejecting hostnames, wildcard, LAN, and public addresses. `port` must be a native TOML integer from 1 through 65535; strings and booleans are invalid. Reject unknown server fields and require restart after changes. These settings apply to the packaged `mymcp` and `mymcp-dev` launchers; direct external Uvicorn invocation remains controlled by that process runner's arguments and is not a supported way to bypass MyMCP's machine-local security boundary. Logging, reload, SSE keep-alive, endpoint paths, identity, protocol, and safety limits remain outside schema version 1. Q10 determines the exact once-per-process design that supplies this snapshot before Uvicorn binds. Non-loopback operation remains deferred until authenticated gateway security exists or the product's machine-local threat model is explicitly revised.
- Decision (Q10): `mymcp` loads host configuration exactly once in `main()`, passes the immutable snapshot into production runtime/application construction, and supplies its server address/port to `uvicorn.run()`; no application factory rereads the source. `create_production_app()` accepts an optional injected `HostConfiguration`, loads exactly once only when none is supplied, passes it to `build_production_runtime()`, and performs no import-time loading. Direct external Uvicorn factory use therefore loads once for application construction while the external process runner owns binding arguments. Development reload has an explicit per-process invariant: its supervisor loads once to validate configuration and choose address/port, each replaceable worker loads once to construct one immutable runtime, and no process rereads or watches `config.toml`; normal production still reads exactly once overall. `HostConfiguration` and nested server/plugin values are frozen and declarations are tuples. Focused tests inject snapshots, count loader/source opens for every startup path, prove ordinary imports and runtime requests perform zero reads, and prove file changes do not affect an existing process. Do not introduce a module-global mutable cache.
- Decision (Q11): The required top-level `schema_version` identifies only the MyMCP host configuration document schema. It is a positive integer, initially exactly 1, owned by `mymcp/host/configuration.py`, represented by a distinct `HostConfigurationSchemaVersion` rather than the generic plugin `ConfigurationSchemaVersion`, and retained in the immutable snapshot. It is independent of the MyMCP distribution/package/server marker, MCP protocol, host plugin API, plugin manifest, plugin/capability, runtime-generation, plugin-data, and Mnemosyne record-schema identities. A present file must declare exactly one supported native TOML integer version; missing, boolean, string, zero, negative, and unknown versions fail boundedly without guessing, coercion, migration, or fallback, while an absent file yields the current schema-v1 default snapshot. Adding/removing/renaming fields or tables, changing field types, required/optional status, defaults, meaning, ordering, duplicate semantics, or adding Phase 3 loading-specific fields requires a new host configuration schema version. Contract-preserving fixes do not; source-safety envelope changes such as increasing the byte limit require explicit version-impact review but do not automatically change the document schema. A future host may intentionally support multiple versions only through explicit parsers and tests; it never rewrites files automatically, a new version does not automatically remove v1, and dropping support requires an explicit compatibility and release decision.
- Decision (Q12): Defer operator-configured public Tool bindings entirely to Phase 3. Schema version 1 contains no `[bindings]` table or binding fields, supports no aliases, renaming, overrides, or dynamic endpoint names, and preserves the existing source-controlled Mnemosyne compatibility bindings plus host-reserved `list_tools` and `mymcp_*` names. External plugin declarations express plugin desired state only, not capability or public-name claims. A safe binding requires a validated qualified capability identity, which this foundation cannot establish before Phase 3 validates external manifest identity, capability inventory/versions, loaded definitions, contribution parity, and collisions. Phase 3 must define binding semantics through an explicit host-configuration schema version change, likely version 2, rather than silently expanding version 1.
- Decision (Q13): Create `docs/CONFIGURATION.md` as the canonical detailed operator guide for XDG path resolution, complete schema-v1/default/example behavior, loopback-only server address and port configuration, plugin desired state and unsupported enablement, restart semantics, source-safety and permission rules, bounded errors, direct-Uvicorn behavior, secret prohibition, and schema compatibility. Update `README.md` with quick setup/examples and a link; update `docs/ARCHITECTURE.md` with `mymcp/host/configuration.py`, ownership/import boundaries, immutable snapshot flow, launcher/bootstrap sequencing, and per-process development reload; update `docs/GLOSSARY.md` with MyMCP host configuration, host configuration schema version, and external declaration desired-state terminology; update `docs/PLUGIN_ARCHITECTURE.md` with the configuration foundation before Phase 3 plus its schema-v1 and loading/binding deferrals; and update `VISION.md` and root `AGENTS.md` current status when delivery occurs without changing product boundaries. Do not change `docs/MANUAL.md`, `docs/GETTING_STARTED.md`, or Mnemosyne-specific configuration guidance. After S1, separately propose the required consent-gated living-roadmap revision for the approved XDG and `[server]` decisions.
- Version-impact decision: Target MyMCP `0.3.0` for both distribution/package and endpoint server marker and introduce MyMCP host configuration schema 1. All other identity/version dimensions remain unchanged for the reasons recorded in Risks / decisions; no Tool-definition ledger entry changes.
