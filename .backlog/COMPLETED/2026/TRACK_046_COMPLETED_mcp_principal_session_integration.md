Problems (PORE)
- P1: As a MyMCP operator, I cannot carry an authenticated normalized principal safely across MCP interactions, because the current principal-aware application seam authenticates and then immediately delegates each request without a host-owned MCP session.
- P2: As a future Governance layer, I cannot safely bind later policy decisions to one authenticated client interaction and one runtime generation, because no immutable session context exists between Authentication and MCP dispatch.
- P3: As a MyMCP user, I need registered-client sessions to preserve the existing local-first and least-privilege boundaries, because a session must not become a substitute for authentication, Tool authority, approval, credential storage, or plugin access.

Objective
- Add a bounded, Authentication-method-neutral, process-local MCP session integration that binds one normalized registered principal to one runtime generation and negotiated MCP context without implementing Governance.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- Follow the system-layer order: HTTP server, Authentication, MCP server, Governance, Plugin runtime, Plugin, and Plugin data or external service.
- Reauthenticate every `/mcp` request before session validation; a session identifier is never Authentication evidence and cannot replace a configured Bearer method.
- Sessions are host-owned, process-local, non-persistent, opaque, bounded, and unavailable to plugins, Tool handlers, Mnemosyne, and durable memory.
- Do not expose credentials, Authorization values, raw Authentication evidence, session identifiers, subjects, request contents, or plugin results through logs, errors, Tool inputs, or durable records.
- A valid session establishes context only. It does not filter Tool discovery, authorize dispatch, satisfy mutation consent, create an approval, grant plugin authority, or change runtime composition.
- Preserve the existing single-user, loopback, local-first model. Do not add remote trust, multi-user tenancy, a session API, session listing, durable storage, renewal, configuration-driven session settings, or a plugin service.
- Preserve Mnemosyne Tool names, schemas, results, errors, gates, configuration, storage, and record contracts.

Why now / impact
- Authentication now produces normalized registered principals through two mutually exclusive production Bearer methods, but the MCP application seam is deliberately pass-through. Sessions are the next required boundary before policy-filtered discovery and per-call authorization can safely act on an authenticated interaction rather than a disconnected request.

Risks / decisions
- Risk: Issuing a session header without reauthentication could make a bearer session ID a credential substitute.
- Risk: Binding only a principal ID string, request ID, or client information could permit cross-context confusion; session validation must bind the normalized `Principal` value and runtime generation.
- Risk: A custom session protocol could harm real MCP client interoperability; the Track must select one documented MCP transport revision and conform exactly before activation.
- Risk: Different failure outcomes could disclose session existence, principal identity, or lifetime; invalid session outcomes must be uniform and content-free.
- Risk: Anonymous has a shared fixed principal and cannot provide a meaningful per-client binding; creating anonymous sessions could imply a false identity boundary.
- Risk: Adding policy or approval behavior prematurely would collapse separate Phase 4 security boundaries.
- Decision: DRAFT baseline is registered-principal-only process-local sessions. Anonymous requests remain stateless unless a documented MCP interoperability requirement requires a separately approved change.
- Decision: The host application boundary, not routes, generic MCP dispatch, Authentication adapters, plugins, or Mnemosyne, owns principal/session lifecycle coordination.
- Decision: The Track will use `Mcp-Session-Id` only if the selected MCP transport revision requires that exact header and semantics; no ad-hoc alternate session header is permitted.
- Decision: Fixed internal bounded lifetime values are preferred over a new host-configuration schema unless planning evidence proves a configuration requirement. Expiry and clock behavior must be deterministic under injected test seams.
- Version impact: Provisional until M1 resolves the exact selected MCP transport revision. This work changes public `/mcp` session behavior and is expected to advance MyMCP distribution/package/server together from `0.7.0` to `0.8.0`. The decision log must record every relevant dimension before activation: endpoint marker, MCP protocol version/negotiation, HTTP routes/header behavior, Authentication contract and adapter types, configuration schemas, host plugin API, manifest schema, external plugin-author contract, worker protocol, plugin/capability contracts, plugin data, runtime generation, policy revision, bindings, Mnemosyne configuration/storage, and record schemas. Every unchanged dimension requires an approved rationale and applicable automated guard.

Decision log
- Decision (dependency): TRACK_046 follows delivered TRACK_042 Authentication contract v1, TRACK_043 operator bearer, TRACK_044 OAuth validation foundation, and TRACK_045 OAuth host integration.
- Decision (layering): Authentication remains upstream and constructs normalized principals only. The host application boundary will bind an already authenticated principal to an MCP session; generic MCP remains Authentication-method-neutral and plugins receive neither session nor Authentication context.
- Decision (security floor): Every request is authenticated before session validation. A valid session is contextual state, never a bearer credential, authorization decision, consent proof, approval, or plugin trust signal.
- Decision (Q1 transport/session contract): MyMCP adopts MCP specification revision `2025-11-25` Streamable HTTP session management. A successful response-bearing `initialize` for a registered principal creates one session and returns exactly one `MCP-Session-Id` response header. The opaque identifier is cryptographically secure and contains only visible ASCII. Each later HTTP request for that session must present exactly one header. Missing session header on a later request returns an empty HTTP `400`; unknown, expired, terminated, stale-generation, or principal-mismatched header returns an empty HTTP `404` without revealing lookup state. `DELETE /mcp` with a valid session header terminates that session and returns HTTP `204`; the existing GET `/mcp` stream requires the same valid session header. This public transport change advances the advertised MCP protocol version from `2024-11-05` to `2025-11-25`; the complete version-impact decision remains required before activation.
- Decision (Q2 protocol and anonymous compatibility): `PROTOCOL_VERSION` advances to `2025-11-25` and is advertised unchanged through initialization and `/version`. Registered principals use the approved Streamable HTTP session contract. Explicitly enabled anonymous access remains stateless: it receives no `MCP-Session-Id`, keeps the existing POST behavior without one, and retains the authenticated keepalive GET behavior without one. An anonymous request carrying `MCP-Session-Id` receives the same empty HTTP `404` as every invalid session lookup. MyMCP does not retain a `2024-11-05` transport-compatibility mode; clients must reconnect using the current protocol for the planned `0.8.0` public release.
- Decision (Q3 session identifier): The host creates each session identifier with `secrets.token_urlsafe(32)`, yielding 256 bits of entropy and exactly 43 unpadded base64url characters. The only accepted grammar is `[A-Za-z0-9_-]{43}`. Registered requests requiring a session must contain exactly one `MCP-Session-Id` header; absent, duplicate, empty, non-ASCII, wrong-length, or invalid-character header values return empty HTTP `400` before MCP body parsing, logging, or dispatch. IDs are opaque exact strings and contain no principal, credential, token, runtime generation, timestamp, or client-derived value. They are never logged, included in JSON, exceptions, or representations, or stored durably.
- Decision (Q4 lifecycle): The application owns one in-memory process-local session store; sessions disappear on restart. Each session has a fixed 30-minute inactivity timeout, refreshed only after a valid authenticated session-bound request, and an 8-hour absolute lifetime that is never extended. The store uses an injected monotonic-clock callable for deterministic tests. Lookup removes expired sessions immediately; no timer, background task, persistence, periodic cleanup, or new configuration setting exists. The store holds at most 128 active sessions. When full, a new registered initialization returns empty HTTP `503` rather than evicting an active session. Valid `DELETE /mcp` removes only the exact validated session.
- Decision (Q5 negotiated context): Each registered session stores only the immutable normalized `Principal`, immutable runtime generation, negotiated MCP protocol version `2025-11-25`, and monotonic creation, last-valid-activity, and absolute-expiry times. Registered `initialize` must offer `2025-11-25` in `params.protocolVersion`; MyMCP returns and stores that version. Every later registered session-bound request must contain exactly one `MCP-Protocol-Version: 2025-11-25` header that matches the stored version; a missing, duplicate, malformed, or unsupported value returns empty HTTP `400` before logging or dispatch. Client information, client capabilities, request IDs, Tool lists, Authentication evidence, policy revision, and mutable negotiation state never enter a session. Generic MCP retains JSON-RPC semantics; the host application uses only minimal parsed method classification to distinguish initialization from a later request.
- Decision (Q6 special requests): A registered response-bearing `initialize` must offer protocol `2025-11-25` and carry neither `MCP-Session-Id` nor `MCP-Protocol-Version`; it creates a new session. A repeated registered initialize is a separate new session only when likewise header-free; initialize carrying either session/protocol header returns empty HTTP `400` and does not terminate an existing session. Every later registered POST request, notification, or response requires valid session and protocol headers; notifications retain HTTP `202` with no body and never create a session. Anonymous access remains sessionless and does not change any Tool discovery, invocation, consent, plugin, or authorization behavior: after anonymous initialization, later anonymous requests require `MCP-Protocol-Version: 2025-11-25` and must not carry a session header. Invalid JSON-RPC shapes retain current protocol outcomes after required transport checks and never create or refresh a session. GET `/mcp` keeps the existing non-resumable keepalive stream: registered access requires valid session/protocol headers, anonymous access requires the protocol header and no session header. DELETE `/mcp` is registered-only, requires valid Authentication/session/protocol headers, removes that session, and returns HTTP `204`; anonymous or invalid-session deletes return the same empty HTTP `404`.
- Decision (Q7 session failures): After successful Authentication, transport-rule violations return empty HTTP `400`: a required session header is missing, duplicated, malformed, or invalid; a session header is prohibited; or a required protocol-version header is missing, duplicated, malformed, or unsupported. Every opaque session-lookup failure—unknown, expired, deleted, different-principal, or different-runtime-generation session identifier—returns empty HTTP `404`. Neither outcome has a JSON-RPC envelope or reveals session ID, principal, expiry, validation branch, or lookup state through response or logs. Existing Authentication failures remain empty HTTP `401`; only enabled OAuth retains its existing Bearer challenge. Active-session capacity exhaustion returns empty HTTP `503`.
- Decision (Q8 application outcome): `mymcp.host.mcp_application` owns a small immutable `MCPApplicationResult` with only the existing JSON-RPC response dictionary or null notification body, one allowed HTTP status, and an immutable response-header mapping. It returns `MCP-Session-Id` only on successful registered initialization. The route authenticates, extracts bounded singleton session/protocol headers, passes plain transport-neutral values and the parsed request body to the application, and serializes the returned outcome through FastAPI `JSONResponse`, `Response`, or the existing stream response. Generic MCP dispatcher output and FastAPI-free MCP modules remain unchanged.
- Decision (Q9 dependency guards): Add AST/import-boundary tests proving `mymcp.host.sessions` depends only on the standard library, Authentication contract `Principal`, and host runtime-generation value; `mymcp.host.mcp_application` may depend on sessions and generic MCP dispatch. Prove `mymcp.authentication`, `mymcp.mcp`, `mymcp.plugin`, `mymcp.plugins`, and all Mnemosyne packages neither import the session module nor expose session identifiers/context. Prove routes do not create, inspect, or mutate sessions directly and remain limited to header extraction and host-application outcome serialization. Test `repr`, logs, errors, handler arguments, and Tool results for absence of session IDs, credentials, subjects, and headers.

It changes only the `/mcp` HTTP transport contract: registered initialization emits `MCP-Session-Id`; later registered traffic requires exact session/protocol headers; explicit registered DELETE terminates a session; session-related 400/404/503 responses are empty. Anonymous mode remains explicitly enabled/disabled by the existing configuration and remains stateless; tools and plugin behavior remain unchanged.
