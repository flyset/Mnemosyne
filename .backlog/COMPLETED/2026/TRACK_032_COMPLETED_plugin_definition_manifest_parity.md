Problems (PORE)
- P1: As a plugin author, I cannot describe one complete inert Tools-only plugin contract for host validation, because Phase 1 defines selected runtime contributions but no strict versioned manifest or immutable `PluginDefinition`.
- P2: As a host maintainer, I cannot prove that activated capabilities agree with their declared identity, compatibility, effects, consent, configuration, data, and requested-authority metadata, because bootstrap currently composes a trusted contribution without definition/manifest parity.
- P3: As a user relying on Mnemosyne, I risk later extraction or external-plugin work freezing an incomplete contract or changing current behavior unless Mnemosyne first validates as one complete bundled declaration while preserving its gated runtime subset.
- P4: As a release maintainer, I cannot rely on a bundled manifest being available after installation, because the package currently has no explicit non-Python resource contract or distribution-level manifest test.

Objective
- Implement the strict shared plugin definition/manifest-v1 contract, validate one complete packaged Mnemosyne manifest against its selected trusted contribution, and fail startup before runtime generation on any inconsistency without changing public Mnemosyne behavior or moving its implementation.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- Execute one declared coherent TDD chunk at a time and update this Track immediately after validation.
- Preserve local-first operation, single-user scope, filesystem truth, least privilege, explicit Tools, operator enablement, and per-call mutation consent.
- Preserve `/mcp`, `/health`, `/version`, the Mnemosyne 0.1.4 server marker, `list_tools`, every current `memory_*` name/order/schema/result/error, `MNEMOSYNE_*`, `~/.mnemosyne`, storage, records, and consent behavior.
- Keep manifests and definitions inert: they contain no executable import, module, class, command, arguments, handlers, configuration or secret values, arbitrary paths, public Tool names, enablement, approval claims, or granted authority.
- Keep static bootstrap explicit and source-controlled. Do not add filesystem scanning, configured imports, entry-point discovery, dynamic loading, dependency resolution, installation, or network access.
- The complete Mnemosyne manifest declares all possible memory Tools; startup gates continue to select only the enabled runtime subset.
- Trusted effect and consent metadata remain internal and are not projected as public MCP annotations.
- Candidate validation must fail before runtime generation and return no partial runtime.
- Do not move or duplicate Mnemosyne configuration, memory-domain code, MCP adapters, Tool definitions, handlers, cursor state, locks, or storage implementation in this Track.

Decision log
- Decision: Begin with planning only. No implementation-driving test, production module, manifest resource, package configuration, documentation contract, or memory record changes while this Track remains DRAFT.
- Decision: The living roadmap revision 4 and `docs/PLUGIN_ARCHITECTURE.md` Phase 2 are authoritative; this Track implements definition/manifest parity and declaration packaging but not vertical extraction.
- Decision (Q1): Keep the implemented identity, version, kind, effects, consent, and binding primitives in `mymcp/plugin/contracts.py`. Add `mymcp/plugin/definition.py` for immutable manifest version, title/description, host-API interval, capability-contract version and declaration, bounded configuration declaration, secret-reference slot, plugin-data schema version, requested authority, and complete `PluginDefinition` values. Add `mymcp/plugin/manifest.py` for strict byte/mapping parsing, compatibility and parity validation, and bounded errors. These generic modules import no concrete plugin, Tool package, host bootstrap, route, or domain code.
- Decision (Q2): Manifest schema version is exactly integer `1`. Titles are nonempty control-free Unicode bounded to 128 characters; descriptions are nonempty control-free Unicode bounded to 4096 characters. Host-API and plugin-data schema versions are actual integers from 1 through 255; ranges require minimum no greater than maximum. Plugin and capability-contract versions use the existing strict bounded SemVer grammar through distinct semantic types. Plugin and capability IDs retain their current 64-character grammars; secret slots use the capability-local lowercase-underscore grammar. Manifests contain at most 64 unique capabilities and 32 unique secret slots.
- Decision (Q3): `configuration` requires schema version `1` and a root object schema. The closed schema subset admits only `type`, `properties`, `required`, `additionalProperties`, and `items`; supports object, array, string, integer, number, boolean, and null types; requires `additionalProperties: false` for every object; requires `items` for arrays; bounds object properties to 32 and nesting depth to four; and requires unique `required` names that exist in `properties`. Unknown keywords, references, composition, defaults, examples, formats, patterns, and configuration values are rejected. Mnemosyne declares an empty object because its existing compatibility configuration is not moved into host-owned plugin configuration in this Track.
- Decision (Q4): Requested filesystem authority is a unique closed subset of `data_read`, `data_write`, `state_read`, `state_write`, `cache_read`, and `cache_write`; requested network authority is an actual boolean. The shape admits no paths, globs, hosts, ports, URLs, commands, environment names, or values and grants no authority. Mnemosyne requests `data_read` and `data_write` with network false as logical requirements; this Track neither issues plugin directories nor changes or claims enforcement over the existing `~/.mnemosyne` compatibility boundary.
- Decision (Q5): `parse_manifest_mapping()` accepts only an already-decoded mapping and performs strict structural conversion. `parse_manifest_bytes()` accepts at most 64 KiB, requires strict UTF-8 and a JSON object root, rejects duplicate object keys during JSON decoding, and delegates to the mapping parser. Neither accepts a path or reads a package. Explicit bootstrap obtains bytes from exactly `mymcp.plugins.mnemosyne` resource `manifest.json` through `importlib.resources`; no caller can select the package or resource name and no scan, metadata entry point, configured import, or network discovery occurs.
- Decision (Q6): `mymcp/plugin/manifest.py` exposes one generic validation boundary over a parsed manifest definition, adapter-returned definition, selected `PluginContribution`, and supported host API `1`. Validation requires exact definition equality, compatible host-API interval, matching plugin identity/version, an ordered selected subsequence of the complete declared capabilities, and exact selected effect/consent metadata. Capability-contract versions remain declaration parity because `PluginContribution` intentionally carries runtime metadata rather than duplicating declaration versions. Validation returns no partial object and finishes before composition or generation creation.
- Decision (Q7): The trusted adapter exposes `mnemosyne_plugin_definition()` and derives it plus contribution policy from one ordered canonical declaration table rather than maintaining a second effect/consent inventory. Mnemosyne retains plugin version `0.1.0`; each initially declared capability contract is version `1.0.0`; configuration is the empty closed object, secret slots are empty, plugin-data schema version is `1`, and requested authority is data read/write with no network. The packaged manifest remains an independent inert declaration whose parity check detects drift; public MCP Tool definitions remain canonical in their current Tool packages.
- Decision (Q8): Add package markers for `mymcp/plugins/` and `mymcp/plugins/mnemosyne/`, and declare exactly `"mymcp.plugins.mnemosyne" = ["manifest.json"]` under `[tool.setuptools.package-data]`. Do not use `MANIFEST.in`, broad JSON patterns, data-files, or entry points. Add `build`, `setuptools>=61`, and `wheel` to the test extra so a subprocess can build a wheel offline with no build isolation; inspect it through standard-library `zipfile`, require the exact package markers and manifest resource, parse the packaged bytes, and reject unintended files in that concrete package.
- Decision (Q9): Use one `PluginContractError(ValueError)` carrying a closed machine-readable code and one bounded deterministic message. Codes distinguish resource size/encoding/JSON/duplicate/root failures, unknown or invalid manifest fields, unsupported versions/kinds, duplicate declarations, invalid configuration/authority, host incompatibility, definition mismatch, contribution identity/version mismatch, undeclared capability, ordering error, and effect/consent mismatch. Errors expose no resource bytes, submitted values, absolute paths, arbitrary exception text, or traceback.
