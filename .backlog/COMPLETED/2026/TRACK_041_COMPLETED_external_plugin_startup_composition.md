Problems (PORE)
- P1: As the MyMCP operator, I cannot compose an independently installed plugin into MyMCP, because an explicitly enabled external declaration currently fails as unsupported before any manifest or implementation is loaded.
- P2: As the MyMCP operator, I need only plugins I explicitly configure and enable to be considered, because package, directory, manifest, or entry-point autodiscovery would weaken deterministic startup and operator control.
- P3: As the MyMCP maintainer, I need inert compatibility checks to occur before external implementation import where possible, because incompatible metadata should fail without executing operator-installed code.
- P4: As the MyMCP maintainer, I need loaded definitions, contributions, capabilities, and public bindings validated as one complete candidate composition, because a partial or collision-prone runtime would make discovery and dispatch inconsistent.
- P5: As the Mnemosyne user, I need every existing memory Tool, configuration, storage, consent, and compatibility identity preserved while external composition is introduced.

Objective
- Add deterministic startup composition for explicitly configured, explicitly enabled, operator-installed and operator-trusted external plugins, with pre-import inert validation where possible and one immutable runtime constructed only after the complete composition is valid.

Non-negotiables
- All implementation follows TDD: a focused failing test, the smallest passing implementation, then refactoring and validation.
- External plugins are considered only through exact declarations in the selected MyMCP host configuration; there is no package, directory, manifest, filesystem, Python entry-point, registry, marketplace, or network autodiscovery.
- Absence from configuration and `enabled = false` both mean no external manifest access, implementation import, Tool exposure, or runtime contribution.
- Any manifest or implementation locator is explicit operator configuration and must be introduced through a new host-configuration schema version; schema version 1 must not be silently expanded.
- Enabled external implementation code is operator-trusted code that may execute in the MyMCP process with that process's authority; compatibility validation is not a safety assessment or isolation guarantee.
- Inert manifest metadata, host-API compatibility, configured identity, plugin identity/version, and capability identities/versions are validated before implementation import where possible.
- Loaded definitions, selected contributions, capability parity, host-owned public bindings, reserved names, and collisions are validated before runtime construction.
- Startup constructs exactly one complete immutable runtime generation or fails clearly without publishing a partial runtime.
- Configuration, plugin, implementation, or enablement changes require server restart.
- Preserve local-first, single-user, least-privilege, thin-HTTP, explicit-bootstrap, and side-effect-free ordinary-import boundaries.
- Preserve every existing Mnemosyne plugin, `memory_*`, `MNEMOSYNE_*`, `~/.mnemosyne`, storage, record, logging, consent, and capability-contract identity.
- Do not add host-managed installation, dependency resolution, Python environments, plugin configuration values or secrets, upgrades, rollback, hot activation, runtime switching, lifecycle management, sandboxing, isolation, filesystem/network restriction, supervision, killability, resource control, or plugin-safety claims.

Risks / decisions
- Risk: A locator design can become de facto autodiscovery if the host probes packages, directories, conventional filenames, entry-point groups, or fallback locations.
- Risk: Importing a Python module executes code; pre-import manifest validation reduces incompatible execution but does not make an enabled plugin safe.
- Risk: A path-based manifest contract can expose local details or weaken source-safety guarantees unless reads and failures are bounded deliberately.
- Risk: Freezing an external Python entrypoint creates a public plugin-author contract that requires explicit compatibility and version governance.
- Risk: Public Tool default names can become unstable or collide as plugins evolve unless binding precedence and persistence decisions are explicit.
- Risk: Supporting multiple host-configuration schemas can accidentally merge semantics or reinterpret schema-v1 desired state.
- Risk: Development reload has separate supervisor and worker processes; external imports and validation must follow the approved per-process model without implying hot activation.
- Risk: Broadening bootstrap can violate generic/concrete dependency boundaries or cause ordinary imports to execute plugin code.
- Decision: External plugins are never autodiscovered. Only exact host-configuration declarations are candidates, and only declarations with explicit `enabled = true` may proceed to external manifest validation and implementation import.
- Decision: Unconfigured and disabled plugins cause no external manifest access, implementation import, contribution, binding, or Tool exposure.
- Decision: Plugin changes take effect only after server restart; there is no runtime plugin lifecycle.
- Decision: Enabled external code is operator-trusted in-process code. MyMCP validates compatibility and composition, not provenance, benign behavior, authority restriction, or safety.
- Version impact: Approved for activation review. Bump the MyMCP distribution/package and endpoint-owned server marker together from `0.3.0` to `0.4.0` because this backward-compatible minor release adds the first supported external startup-composition capability, host-configuration schema 2, and public external plugin-author contract 1. Add host-configuration schema 2 while retaining an exact schema-v1 parser and behavior; schema 2 adds only explicit external `manifest_path` and `module` locators to the existing declaration identity and enablement fields. Introduce external plugin-author contract 1 through the versioned `mymcp_plugin_v1` entrypoint. Preserve MCP protocol `2024-11-05`, host plugin API 1, manifest schema 1, and the absence of a worker protocol because external plugins remain ordinary Tools-only definitions/contributions using the existing inert manifest and composition semantics without a process protocol. Preserve every plugin-owned configuration schema, Mnemosyne plugin `0.3.0`, `memory_recall` capability `1.2.0`, the other seven Mnemosyne capability versions `1.1.0`, every plugin-data schema, policy identity, opaque per-start runtime-generation semantics, and memory record schemas because this Track changes no plugin-owned configuration, Mnemosyne Tool definition/result/error, gateway policy, plugin data, runtime publication model, or memory persistence contract. Preserve host-reserved names and pinned Mnemosyne bindings; add only the already-targeted deterministic external default `<plugin-id>__<tool-local-id>`, with operator-defined persisted bindings deferred. Retain `enabled_plugin_unsupported` for schema-v1 enabled declarations; schema-v2 enabled declarations intentionally replace that bounded unsupported state with validated composition. Existing Mnemosyne capability-ledger entries must pass unchanged because no Mnemosyne Tool definition changes.

Decision log
- Decision (operator direction): MyMCP will not autodiscover external plugins. An external plugin must be explicitly declared and explicitly enabled in host configuration before the host considers its inert metadata or implementation.
- Decision (planning boundary): This DRAFT records Phase 3 planning only. It authorizes no implementation, implementation-driving test, configuration-schema change, package import contract, version change, documentation change outside this Track, or roadmap mutation.
- Decision (Q1/Q2): Host-configuration schema 2 retains optional `[server]` and ordered `[[plugins]]`. Every schema-v2 plugin table contains exactly required `id`, native boolean `enabled`, absolute string `manifest_path`, and importable dotted string `module`; all four are required even when disabled. `manifest_path` rejects relative paths, `~`, environment expansion, NUL, and explicit `.` or `..` components. `module` is at most 255 ASCII characters and consists only of nonempty dotted Python-identifier components; relative module names and leading, trailing, or repeated dots are invalid. The host does not trim, case-fold, resolve, canonicalize, expand, derive, search, insert a path, or try an alternate value.
- Decision (Q3): Dispatch parsing by the required native integer `schema_version` before interpreting plugin tables. Preserve schema 1 exactly, including `id`/`enabled`-only declarations and `enabled_plugin_unsupported` for an enabled v1 declaration. Parse schema 2 independently; never merge, rewrite, migrate, or assign loading semantics to v1. An absent file continues to produce the current immutable schema-v1 bundled-only defaults.
- Decision (Q4): Read only an enabled declaration's exact absolute `manifest_path`, at most once in a composing process and at most 64 KiB. Reject a symlink/reparse immediate parent or final source, non-directory parent, non-regular source, and on POSIX a parent or file writable by group or others. Use available no-follow, descriptor, identity, type, size, permission, and pre/post source-state checks; reject detectable replacement or mutation, require strict manifest parser UTF-8/JSON behavior, and perform no retry, alternate-path fallback, directory scan, conventional-filename lookup, or package-resource lookup. Ancestors above the immediate parent follow the same accepted-anchor model as host configuration. Failures expose only approved bounded codes/messages.
- Decision (Q5): After complete configuration validation and limits, safely read and strictly parse every enabled manifest in declaration order before importing any external implementation. For every parsed manifest, require configured ID equality, host API 1 compatibility, valid plugin identity/version, and valid complete capability identities/versions. If any enabled manifest fails, import no external implementation. Identity mismatch and all other failures omit configured and declared identities from results and logs.
- Decision (Q6): External plugin-author contract 1 requires the configured module to expose exactly one zero-argument callable named `mymcp_plugin_v1`. One invocation returns an exact immutable host-owned `PluginAdapter` value containing one `PluginDefinition` and one selected `PluginContribution`. The callable receives no host context, registry, configuration values, secret values, binding authority, filesystem capability, lifecycle handle, or host service. Missing, non-callable, raising, or wrong-type entrypoints fail boundedly.
- Decision (Q7): Keep host plugin API 1. External plugins still use the existing Tools-only logical manifest, definition, contribution, effect/consent, parity, and composition contracts. External plugin-author contract 1 separately versions the physical in-process entrypoint; an incompatible entrypoint contract or logical host contract requires an explicit future version decision.
- Decision (Q8): Only explicit enabled schema-v2 declarations reach external manifest access and implementation import. After every enabled manifest passes pre-import validation, `mymcp.host.bootstrap` invokes the narrow external loader in declaration order. Reject duplicate module locators before import; call `importlib.import_module` once and `mymcp_plugin_v1` once per enabled declaration per composing process. No ordinary package import, configuration parse/validation, disabled/unconfigured declaration, runtime request, or existing runtime rereads or imports external code. Development replacement workers remain separate composing processes.
- Decision (Q9/Q10): Implement only deterministic external defaults `<plugin-id>__<tool-local-id>`. Preserve host-reserved names and prefixes plus pinned Mnemosyne compatibility bindings ahead of these defaults. Defer persisted operator-defined bindings, aliases, renames, stale-capability behavior, and binding migration to a later Track and explicit host-configuration schema decision.
- Decision (Q11): Compose bundled plugins first in existing explicit order, then enabled external plugins in schema-v2 declaration order without sorting. Within each plugin, preserve the selected capability order validated against manifest declaration order. Generate external bindings in that order. The same complete surface drives plugin inventory, registry order, `tools/list`, host `list_tools`, dispatch, qualified origins, trusted effects/consent, and bindings; host `list_tools` remains first and Mnemosyne retains its current order and names.
- Decision (Q12): Add host-owned `ExternalPluginLoadError` with one stable code and fixed non-identifying message. The approved code vocabulary covers `external_plugin_limit_exceeded`, `external_manifest_unsafe_path`, `external_manifest_not_regular`, `external_manifest_unsafe_permissions`, `external_manifest_unreadable`, `external_manifest_too_large`, `external_manifest_source_changed`, `external_manifest_invalid`, `external_manifest_identity_mismatch`, `external_manifest_host_api_incompatible`, `external_plugin_import_failed`, `external_plugin_entrypoint_invalid`, `external_plugin_contract_invalid`, and `external_plugin_composition_invalid`. Error precedence is configuration source/schema, bundled identity collision, limits and duplicate module locator, all enabled manifest source/parse/identity/host-API checks, implementation imports/entrypoints/parity, generated bindings/final composition, then generation. Wrap underlying errors without chaining details; every failure returns no runtime.
- Decision (Q13): Allow at most 32 enabled external plugins and at most 256 selected external capabilities across the complete enabled external set. Existing 64 KiB host configuration, 64 KiB per-manifest, and 64 capabilities per manifest remain. Enforce enabled-plugin and aggregate-capability limits before importing the exceeding candidate; each enabled manifest is read at most once and each enabled module/entrypoint is invoked at most once per composing process. Disabled declaration count remains bounded by the configuration source rather than a separate limit.
- Decision (Q14): Preserve the exact `mymcp.host.configuration` event shape; it may report `schema_version=2` and the existing declaration/enabled counts. Add one `mymcp.host.bootstrap` terminal event per composition attempt: INFO `runtime_composition outcome=loaded bundled=<count> external=<count> capabilities=<count>` after successful runtime construction, or ERROR `runtime_composition outcome=error code=<stable_code>` before propagating a bounded failure. Log no path, plugin ID, module, manifest content, configuration value, exception detail, traceback, provenance assessment, or safety claim.
- Decision (Q15): Add narrow generic host external-loading support under `mymcp/host/`; it may depend only on standard library, immutable host configuration values, and generic plugin contracts. `mymcp/plugin/` remains path/import/concrete-plugin-free. Only explicit bootstrap may invoke external loading; routes, MCP modules, runtime requests, app imports, settings, and plugins do not. Extend AST and subprocess import-boundary coverage accordingly.
- Decision (Q16): Apply the complete approved `0.4.0`, schema-2, external-author-contract-1 version-impact decision recorded above before release/documentation completion. No Mnemosyne capability-ledger entry changes.
- Decision (Q17): Update `README.md`, `VISION.md`, `docs/ARCHITECTURE.md`, `docs/PLUGIN_ARCHITECTURE.md`, `docs/GLOSSARY.md`, `docs/CONFIGURATION.md`, root `AGENTS.md`, and applicable host/plugin scoped guidance. Add a test-owned minimal external plugin fixture that is excluded from wheel package data. Update release documentation only if release publication is separately included; do not change Mnemosyne `docs/MANUAL.md` or `docs/GETTING_STARTED.md` because their agent-memory operating contract is unaffected.
- Decision (Q18): Keep TRACK_041 as one vertical Phase 3 Track with dependency-ordered coherent TDD chunks. A schema/preflight-only completed Track would leave a deliberately temporary unusable enabled state; the existing S3-S8 sequence provides reviewable boundaries without publishing that intermediate outcome. Persisted operator bindings remain the clean deferred follow-on.
