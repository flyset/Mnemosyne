# MyMCP 0.4.0 Release Notes: external plugin startup composition

## External startup composition

MyMCP/`mymcp` `0.4.0` composes operator-installed, operator-trusted external
plugins at process startup from validated host configuration schema 2. The host
performs complete inert-manifest preflight before importing enabled plugin code,
loads declared adapters in deterministic order, validates exact
definition/contribution parity, assigns kind-qualified Tool bindings, and builds
one immutable runtime generation.

Plugin configuration and installed code are fixed for the life of the process.
Changes require a server restart. MyMCP validates compatibility and composition;
it does not establish that an operator-installed plugin is safe.

## Compatibility preserved

- MCP protocol `2024-11-05`, host plugin API 1, and plugin manifest schema 1
  remain unchanged.
- The bundled Mnemosyne plugin remains `0.3.0` and is composed first.
- `memory_recall` remains capability contract `1.2.0`; the other seven
  Mnemosyne capabilities remain `1.1.0`.
- Existing Mnemosyne Tool names, definitions, order, bindings, mutation gates,
  storage, and explicit-consent behavior remain unchanged in bundled-only
  operation.
- Host configuration schema 1 remains supported and retains its bounded
  `enabled_plugin_unsupported` behavior. Schema 2 enables validated external
  startup composition.

## Trust and lifecycle boundaries

- MyMCP does not install plugins, resolve dependencies, manage plugin
  environments, or hot-activate changed code.
- External plugin modules run in the host process with the operator's authority;
  this release adds no process isolation, sandbox, worker protocol, resource
  enforcement, or host-granted filesystem/network permissions.
- Runtime lifecycle management, plugin isolation, gateway governance, and
  reusable service exposure remain deferred.
